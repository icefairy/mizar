# 发明专利技术交底书

## 发明名称

一种零依赖单文件可自举的离线 AI 智能体框架及其三层扩展架构

---

## 一、技术领域

本发明涉及人工智能智能体（AI Agent）技术领域，具体涉及一种面向离线/内网环境的零依赖、单文件分发、可自举扩展的 AI 智能体运行框架及其多层扩展架构、缓存友好的循环执行机制、实时纠正确认协议与热重载管理方法。

---

## 二、背景技术

### 2.1 现有 AI Agent 框架的局限性

当前主流 AI 智能体框架（如 Pi Agent、Claude Code、Goose、Crush 等）在设计上均存在以下共性缺陷：

**（1）依赖运行时环境**：Pi Agent 构建于 Node.js 之上，需安装 npm 及大量 node_modules 依赖包（数百 MB），在内网/离线/气隙（air-gapped）环境下无法部署。类似地，Claude Code、Goose 等均依赖 Node.js 或 Python 运行时。

**（2）依赖外网分发能力**：所有主流框架的插件/扩展/技能均需通过网络分发（npm registry、GitHub 下载等），在内网隔离环境中扩展能力完全失效。

**（3）无法通过安全审查**：企业级内网环境（银行、军工、能源、政务等）对软件有严格的依赖审计和安全审查要求。依赖树中包含 npm 数万个小包，投毒攻击面巨大，难以通过安全合规审查。

**（4）离线自举能力缺失**：现有框架缺少"智能体自己写扩展扩展自己"的闭环能力——写扩展后仍需人工安装依赖、修改配置、重启服务才能生效。

**（5）LLM 缓存命中率低**：现有 Agent 框架在循环执行中频繁修改系统提示词（system prompt）中嵌入的动态内容（时间戳、工具列表、技能内容等），导致 LLM 服务商的前缀缓存（prefix cache）命中率极低，API 调用成本居高不下。

### 2.2 现有技术尝试及不足

| 技术方案 | 核心思路 | 不足 |
| --- | --- | --- |
| Rust + 内嵌 JS 引擎 | 消除 Node 依赖 | 仍需兼容 npm 生态，间接依赖外网 |
| Python + PyInstaller | 打包为单文件 | Python 运行时体积大（>40MB），自举编码成功率低 |
| 容器化部署（Docker） | 封装依赖 | 依赖镜像分发，内网仍需镜像仓库 |
| 纯 Go 实现 | 静态编译单文件 | 缺少插件扩展机制，无法自举 |

### 2.3 本专利的技术问题

因此，本领域亟待解决的技术问题是：**如何构建一个零运行时依赖、单文件可分发、可在完全离线环境下自举扩展、且对 LLM 前缀缓存友好的 AI 智能体框架。**

## 三、发明内容

### 3.1 总体技术方案

本发明提供一种零依赖单文件可自举的离线 AI 智能体框架（以下简称"本框架"），其核心特征为：

**（1）单二进制静态编译**：框架核心完全由 Go 语言编写，静态编译为单文件可执行二进制（~20MB），无需任何运行时依赖（无 Node.js、无 Python、无 npm、无 Docker）。安装 = 复制一个文件。

**（2）三层扩展模型**：通过"技能层 + 插件层 + 工具层"三层架构实现能力的可扩展性，三层互不阻塞、各自独立扩展。

**（3）内嵌编译引擎实现自举闭环**：在二进制内部嵌入 TypeScript 编译器（esbuild Go 库）和 JavaScript 解释引擎（goja），使智能体能在运行时自行编写、编译、加载 TypeScript 插件，无需外部编译链。

**（4）缓存友好的系统提示词管理**：采用"系统提示词字节级强冻结 + 技能索引按需加载 + 禁用工具只改注册表"的三级缓存保护策略，保证 LLM 前缀缓存命中率。

**（5）实时纠正确认协议**：通过 WebSocket 事件流 + 线程安全纠槽位机制，实现用户在看到 Agent 中间输出后实时纠正方向的秒级响应。

**（6）钩子挂载点与缓存影响分级**：11 个挂载点全覆盖 Agent 循环，每个挂载点标注缓存影响等级（🔴严重/🟡中等/🟢安全），指导插件开发者避免缓存破坏。

### 3.2 三层扩展模型（核心创新点之一）

本框架的能力扩展分为三层，各层载体、扩展方式和自举机制如下：

| 层 | 载体 | 内容类型 | 自举方式 |
| --- | --- | --- | --- |
| **技能层** | SKILL.md（Markdown 纯文本） | 指导智能体"怎么做"的知识和流程 | 智能体写文档即生效，无需编译 |
| **插件层** | .ts / .js 文件 | 可执行的新工具/新能力代码 | 智能体写代码 → 内嵌编译器转译 → 热加载注册 |
| **工具层** | MCP 协议服务器（stdio/HTTP） | 任意语言实现的协议服务 | 启动进程/连接端点即接入 |

三层的关系与扩展流程：

```
用户需求
  │
  ▼
智能体判断是否已有能力可用
  ├── 有 → 直接执行
  └── 无
       │
       ├── 能否用文档描述（知识/流程）→ 写 SKILL.md（技能层）
       │
       ├── 是否需要可执行代码 → 写 .ts 插件（插件层）
       │      │
       │      ▼
       │   esbuild 编译（内嵌，毫秒级，零外网）
       │      │
       │      ▼
       │   goja 执行 → 新工具热注册（无需重启）
       │
       └── 是否需要外部服务 → 启动 MCP 服务器（工具层）
```

### 3.3 内嵌编译引擎与热重载机制（核心创新点之二）

本框架在内嵌二进制中实现了完整的 TypeScript 到 JavaScript 编译管线：

**编译流程**：

1. 智能体编写 `.ts` 插件文件
2. 框架通过内嵌的 esbuild Go 库将 TypeScript 转译为 ES2018 JavaScript（类型擦除，不做类型检查——适合自举场景，立即能跑、跑错再修）
3. 转译后的 JavaScript 代码在 goja（纯 Go 实现的 ECMAScript 引擎）中执行
4. 框架扫描全局对象，自动发现以 `tool_` 前缀导出的函数，注册为可用工具
5. 同时扫描 `command_`（斜杠命令）、`rpc_`（JSON-RPC 方法）前缀函数，分别注册

**热重载设计**：

- 每个插件文件运行在独立的 goja 引擎实例中，实现插件间隔离
- 文件修改时间（modTime）变化时触发增量重载：旧引擎关闭 → 新引擎加载 → 工具原子替换
- 强制重载模式（`/reload`）：忽略 modTime，重新执行所有插件，用于宿主函数注入后同步

**宿主函数注入**：

- Go 侧向 JS 引擎注入安全受控的宿主函数集：`http_request`（统一 HTTP，支持任意方法）、`json_decode/encode`、`fs_read/fs_read_range`（有界文件读取）、`fs_write`、`fs_list`、`shell_exec`（白名单命令）、`llm_chat`（调用 LLM，实现自举闭环）、`log`、`sleep`、`ws_emit`（WebSocket 广播）、`ws_connect/ws_send/ws_onmessage/ws_close`（WS 客户端桥）
- 文件读取限制：`fs_read` 上限 10MB，`fs_read_range` 单次 4MB（支持 seek 分片）
- Shell 命令白名单：仅允许预注册的安全命令，拒绝 `rm -rf` 等危险模式
- 执行超时：每个工具调用 30 秒超时，超时自动中断

### 3.4 缓存友好的系统提示词管理机制（核心创新点之三）

本框架提出三级缓存保护策略，最大化 LLM 前缀缓存（prefix cache）命中率：

**第一级：系统提示词字节级强冻结**

- `SystemPrompt()` 方法在首次调用时构建完整的系统提示词（含系统描述 + 技能索引 + 工具列表），并缓存在内存中
- 在插件热重载之前，任何后续调用都返回完全相同的字符串（字节级一致）
- 只有显式调用 `ReloadTools()` 时缓存才失效——这是显式的性能权衡，调用方仅在确实新增工具时使用

**第二级：技能索引按需加载**

- 默认采用"索引模式"：系统提示词中只列出技能名称、描述和文件路径，不包含技能正文
- 技能文件内容变化不改变系统提示词，前缀缓存稳定
- 智能体需要某技能时，用 `read` 工具读取对应文件路径——正文内容作为用户消息追加，不在系统前缀中

**第三级：禁用工具只改注册表**

- 当用户禁用某工具时，仅在插件管理器的工具注册表中摘除该工具
- 系统提示词不变（工具列表字节稳定），前缀缓存不受影响
- 智能体看不到被禁用的工具名称，自然不会调用

**压缩器缓存保护**：

- 会话压缩为低频操作（仅在 token 超限时触发）
- 压缩摘要以固定格式插入系统消息之后，重新建立可缓存前缀
- 摘要请求使用独立请求（带 `X-Mizar-Request: summarize` 请求头），prompt 前缀与主对话不同，天然不污染主对话缓存

### 3.5 实时纠正确认协议（核心创新点之四）

本框架实现了一种基于 WebSocket 的实时纠正确认协议，使外部用户能在 Agent 执行过程中实时干预：

**协议架构**：

```
┌─────────┐                          ┌───────────┐
│ 客户端   │  ← 事件流（只读）      │   Agent   │
│(前端/脚本)│── agent.run (异步) ──► │  循环     │
│         │  ◄── llm_response ─── │           │
│         │  ◄── tool_call ────── │           │
│         │  ◄── tool_result ──── │           │
│         │── agent.steer (立即) ──► 注入纠正  │
│         │  ◄── ack (秒回) ───── │           │
│         │── agent.abort ────────► 循环终止  │
└─────────┘                          └───────────┘
```

**关键设计**：

- `agent.run` 在 WebSocket 通道中异步执行（不阻塞读循环），结果通过事件流推回
- `agent.steer` 线程安全写入纠槽位，服务端秒回 `ack` 确认
- Agent 循环在**下一次 LLM 调用前**检查纠槽位，将纠正消息以 `【用户快速纠正】` 前缀注入
- 多条纠正只保留最新一条（用户最新意图优先）
- `agent.abort` 设置原子标志，循环在下一个检查点停止
- 纠正确认的缓存影响为 🟡 中等：纠正注入在消息序列末尾，system 前缀与早期历史仍可命中

### 3.6 钩子挂载点系统与缓存影响分级（核心创新点之五）

本框架设计了一套全环节覆盖的钩子挂载点系统：

**11 个挂载点**：

| 挂载点 | 触发时机 | 缓存影响 | 可修改字段 |
| --- | --- | --- | --- |
| RunStart | Run 开始、task 已就绪 | 🟢 安全 | - |
| RunEnd | Run 结束、reply 已生成 | 🟢 安全 | - |
| StepStart | 每步循环开始 | 🟡 中等 | Messages(不建议) |
| StepEnd | 每步循环结束 | 🟡 中等 | - |
| **LLMRequest** | **LLM 调用前** | **🔴 严重** | **Messages** |
| LLMResponse | LLM 调用后 | 🟢 安全 | - |
| ToolCall | 工具调用前 | 🟢 安全 | Tool/Args |
| ToolResult | 工具结果后 | 🟡 中等 | - |
| CompactionBefore | 压缩前 | 🟢 安全 | - |
| CompactionAfter | 压缩后 | 🟢 安全 | Messages(不建议) |
| Error | 任何错误 | 🟢 安全 | - |

**设计原则**：

- 全环节覆盖：Agent 循环每个关键环节都有挂载点
- 多挂载支持：每个挂载点支持多个插件同时注册，按顺序执行
- 非中断观察者：单个挂载函数返回 error 不中断主循环，仅记录日志
- 缓存影响分级：🔴 严重级别挂载点（LLMRequest）默认禁用动态内容注入，文档明确警告

### 3.7 双传输 MCP 客户端

本框架实现了支持两种传输方式的 MCP（Model Context Protocol）客户端：

**（1）stdio 传输**：通过子进程 stdin/stdout 按行通信 JSON-RPC，适用于本地进程型 MCP 服务器。实现细节包括：异步读取循环、pending 请求-响应通道映射、自动丢弃 stderr 防止管道阻塞。

**（2）HTTP (streamable) 传输**：通过 HTTP POST JSON-RPC 通信，支持 SSE（Server-Sent Events）响应格式的解析。实现细节包括：SSE `data:` 行提取、10MB 响应体限制、超时控制。

两种传输方式通过统一的 `Transport` 接口抽象，上层 `Client` 无需感知传输差异。

### 3.8 会话压缩器的切点保护算法

本框架的会话压缩器实现了保证工具调用配对完整性的切点搜索算法：

```
算法步骤：
1. 从消息列表后向前累计 token，直到累计值超过 KeepRecentTokens
2. 在超出点之前寻找最近的合法切点
3. 合法切点定义：
   - 普通 user/assistant 消息 → 可切
   - tool_result 消息 → 不可切（必须跟随其 tool_call）
   - summary 消息 → 不可切（它是压缩产物本身）
4. 切点前消息 → 送入 LLM 生成结构化摘要
5. 重建消息列表：[system] + [摘要] + [切点后的保留消息]
```

**结构化摘要格式**：

```
## Goal [用户目标]
## Progress (Done / In Progress)
## Key Decisions [决策及理由]
## Next Steps [有序步骤列表]
## Critical Context [精确路径/函数名/错误消息]
```

### 5.2 三层扩展的具体实现

**技能层实现**（`internal/skills/` 包）：

- 扫描 `skills/` 目录下所有 `.md` 文件
- 解析 frontmatter（`---` 分隔的 YAML 子集，提取 name/description）
- 支持两种注入模式：全量（默认索引模式）和正文模式
- 索引模式：`RenderIndex()` 只输出 `name + description + path`，正文由 `read` 工具按需加载

**插件层实现**（`internal/plugins/` + `internal/engine/` 包）：

- `Manager.LoadAll()` 扫描 `extensions/` 目录
- `.ts` 文件：`engine.CompileTS()` → esbuild 转译 → goja 执行
- `.js` 文件：直接 goja 执行（跳过编译）
- `collectTools()` / `collectCommands()` / `collectRPC()` 扫描全局函数
- 每个插件独立 `engine.Engine` 实例，插件间隔离
- `Call()` 带 30 秒超时保护

**工具层实现**（`internal/mcp/` 包）：

- `Transport` 接口统一抽象
- `StdioTransport`：启动子进程 → stdin 写 JSON-RPC → stdout 按行读
- `HTTPTransport`：HTTP POST JSON-RPC → 解析响应（含 SSE 支持）

### 5.3 Agent 核心循环伪代码

```go
func (a *Agent) Run(task string) (string, error) {
    msgs := [SystemPrompt(), ...Initial, {User: task}]
    for step := 0; step < MaxSteps; step++ {
        // 1. 检查纠槽位（优先于压缩）
        if steer := a.drainSteer() != nil {
            msgs = append(msgs, {User: "【用户快速纠正】" + steer})
        }
        // 2. 检查 abort
        if a.Aborted() { return "", ErrAborted }
        // 3. 压缩检查
        if a.Compactor.ShouldCompact(EstimateMessages(msgs)) {
            msgs = a.Compactor.Compact(msgs)
        }
        // 4. LLMRequest 挂载点（🔴 严重）
        a.Hooks.fireLLMRequest(msgs)
        // 5. 调用 LLM
        reply := a.LLM.Chat(msgs)
        // 6. 解析模型回复
        req, err := parseCallJSON(reply)
        if err != nil {
            // 错误回喂：把解析错误告诉模型让它修复
            msgs = append(msgs, reply, "解析失败：" + err)
            continue
        }
        if req.Action == "reply" { return req.Text, nil }
        // 7. 工具调用
        out, err := a.Plugins.Call(req.Tool, req.Args)
        msgs = append(msgs, reply, "工具结果：" + out)
    }
    return "", ErrMaxSteps
}
```

## 九、替代方案与扩展
